# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`DemoSolution` is a full-stack Visual Studio 2022 reference solution organized into three
layers — **Data**, **Services**, and **Presentation** — each a solution folder in
`DemoSolution.sln`. It is a work in progress: the Services/Data layers and the Web API are the
mature parts; the Presentation front-ends are in varying stages of completion (React and Angular
are furthest along; Blazor and Razor are default scaffolds; Vue is stubbed).

Backend targets **.NET 8** with **EF Core 9**. SQL Server 2019 is the database.

## Commands

Run from the repo root unless noted.

### Backend (.NET)
- Build everything: `dotnet build DemoSolution.sln`
- Run the Web API: `dotnet run --project Services/DemoWebApi` (Swagger UI at the app root)
- Run all tests: `dotnet test Services/DemoTests/DemoTests.csproj`
- Run one test class: `dotnet test Services/DemoTests/DemoTests.csproj --filter ClassName~ClientServiceTests`
- Run one test: `dotnet test Services/DemoTests/DemoTests.csproj --filter "FullyQualifiedName~ClientServiceTests.CreateClient"`

Note: `Data/DemoSql/DemoSql.sqlproj` is an **SSDT** project — it builds under MSBuild/Visual
Studio on Windows, not via `dotnet build` on macOS/Linux. Excluding it, the rest of the solution
builds cross-platform.

### Front-ends
- React (`Presentation/DemoReact`): `npm run dev` / `npm run build` / `npm run lint`
- Angular (`Presentation/DemoAngular`): `npm start` / `npm run build` / `npm test`
- Vue (`Presentation/DemoVue`): `npm run dev` / `npm run build`
- Blazor Server (`Presentation/DemoBlazor`) and Razor (`Presentation/DemoRazor`):
  `dotnet run --project <path>`

## Architecture

### Layer dependencies (one direction only)
`DemoModels` (plain DTOs, no dependencies) ← `DemoRepository` (EF entities) ←
`DemoServices` (business logic) ← `DemoWebApi` (HTTP). `DemoUtilities` is a leaf of static
helpers used across Services/WebApi. Presentation front-ends consume the Web API over HTTP;
they do **not** reference the .NET projects directly.

### Data layer
- **`DemoSql`** — SSDT project; the schema is the source of truth (`Tables/`, `Views/`).
- **`DemoRepository`** — EF Core entities and `DemoSqlContext`, **generated by EF Core Power
  Tools** from the database (config in `efpt.config.json`). Treat these as generated; regenerate
  rather than hand-editing when the schema changes. `Nullable` is disabled in this project only.
- **`DemoModels`** — the DTOs (`ClientModel`, `UserModel`, `WorkItemModel`, etc.) that cross the
  service boundary and serialize over the API. `Enums.cs` holds shared enums (referenced as
  `static DemoModels.Enums`).

### Audit pattern (pervasive — understand before touching services)
Every core entity has a parallel **`*Audit`** table/entity plus SQL **`*View`** and
**`*AuditView`** views. After any mutating service operation (create/update/delete), the service
opens a **new DI scope**, resolves `IAuditService`, and writes an audit record. When adding a
mutation to any service, follow this convention and write the corresponding audit record.

### Services layer
- Services live in `DemoServices` with an interface in `Interfaces/` and are registered in DI
  (see both `DemoWebApi/Program.cs` and `DemoTests/BaseClasses/TestBase.cs`).
- Base-class chain in `BaseClasses/`: `ConfigurationService` → `ServiceProviderService` →
  `DbContextService`. Concrete services inherit `DbContextService`, which provides
  `IDbContextFactory<DemoSqlContext>`, an `IMemoryCache` with cache options driven by the
  `Demo:CacheSeconds` config value, and the connection string.
- **C# 12 primary constructors** are used throughout services and controllers — match this style.
- Data access uses **`IDbContextFactory`** with short-lived `using (var dbContext = ...)` blocks,
  not an injected long-lived context.
- App configuration is read from the **`Demo`** config section via
  `GetConfigurationKeyValue(key)` / `ConfigurationUtility`.

### Web API layer (`DemoWebApi`)
- Controllers inherit `BaseController` (`[Authorize]`, `[ApiController]`) and resolve services
  by **manually creating a DI scope per action** (`_serviceProvider.CreateScope()` →
  `GetRequiredService<IXService>()`) rather than constructor-injecting the services. New
  controllers should follow this pattern.
- Auth is **JWT**: a custom `JwtMiddleware` runs before authentication, a custom
  `AuthorizeAttribute` guards controllers, and tokens are issued via `JwtTokenService` /
  `JwtTokenController`. Keys/issuer/audiences come from the `Jwt` config section.
- CORS origins and other environment specifics are hard-coded per-environment in `Program.cs`.

### Tests (`DemoTests`)
- **MSTest + Moq**, with EF Core **InMemory** provider (database name `"DemoSql"`). Tests run
  in parallel at method level (`MSTestSettings.cs`).
- `TestBase` builds the service provider, loads `appsettings.json`, and mocks `HttpContext`.
  Known-good record IDs come from `Demo:Test*Ids` config values.
- `TestHelpers/Compare*.cs` provide model-equality assertions; reuse them instead of writing
  ad-hoc field-by-field comparisons.

## CI/CD
`.github/workflows/` builds on `windows-latest` with .NET 8 and deploys to Azure Web Apps on
push to `master` (`master_demosolution.yml` for the main app, `master_wloescher-demowebapi.yml`
for the Web API).
